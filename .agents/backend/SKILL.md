# Backend Skill

## 적용 범위

`lam-api` 백엔드 작업에 적용한다.

대상 예시:
- Go API 서버
- `internal/httpapi` 라우팅
- `internal/config` 설정
- `internal/store` repository
- 관리자 API와 손님용 API

## 기본 원칙

- 기존 Go 구조와 네이밍을 유지한다.
- 표준 라이브러리 `net/http` 기반 라우팅 흐름을 존중한다.
- 프론트 변경으로 백엔드 수정이 필요하면 그 이유를 먼저 설명한다.
- 기존 엔드포인트를 함부로 합치거나 이름을 바꾸지 않는다.
- 입력 구조가 달라질 때는 프론트/백엔드/DB 영향 범위를 함께 고려한다.

## API 규칙

- 손님용 API와 관리자 API를 혼동하지 않는다.
- 관리자 API는 인증 흐름과 기존 프록시 구조를 고려한다.
- 요청 생성, 상태 변경, 삭제는 현재 도메인 흐름에 맞게 유지한다.
- 일반 요청과 특별 요청은 분리된 API 흐름을 유지한다.

## 요청 관련 규칙

- 일반 요청은 `customer_requests` 흐름을 따른다.
- 특별 요청은 `special_requests` 흐름을 따른다.
- 특별 요청 관련 필드를 일반 요청 API payload에 다시 섞지 않는다.
- `바로 전달하기` 요청은 상태 관리가 있다.
- `특별한` 요청은 상세 확인과 삭제 중심이다.

## 저장소 레이어 규칙

- repository 메서드는 기존 에러 처리 방식을 유지한다.
- 입력 검증은 현재 `ErrInvalidInput`, `ErrNotFound` 등 기존 패턴을 우선한다.
- SQL 변경이 필요한 경우 데이터베이스 지침도 함께 확인한다.
- nullable 스캔 문제가 생기지 않도록 `COALESCE` 또는 분리 모델을 적절히 사용한다.

## 설정 규칙

- 기본 API 주소, DB URL, CORS, 관리자 토큰은 기존 config 흐름을 따른다.
- 환경변수 이름을 임의로 바꾸지 않는다.

## 검증

- 사용자가 요청하지 않은 한 `go build ./...`를 실행하지 않는다.
- 검증하지 않은 경우 최종 답변에서 명확히 밝힌다.
