# Frontend Skill

## 적용 범위

`lam-web` 프론트엔드 작업에 적용한다.

대상 예시:
- 손님용 모바일 화면
- 관리자 화면
- 공통 navigation, screen, service 레이어
- CSS 및 반응형 UI
- 요청 작성/확인 UI

## 기본 원칙

- 기존 Next.js App Router 구조와 컴포넌트 분리 방식을 유지한다.
- 손님 화면과 관리자 화면의 역할을 혼동하지 않는다.
- 모바일 우선 UX를 유지한다.
- 사용자가 지정한 파일과 연결된 참조만 우선 확인한다.
- 기존 CSS 톤, 간격, 버튼 밀도, 카드 크기를 존중한다.

## 손님 화면 규칙

- 손님 화면은 빠르고 단순해야 한다.
- 메뉴, 요청, 이벤트 흐름이 자연스럽게 이어져야 한다.
- 관리자 개념이나 운영자용 상태가 손님 화면에 노출되지 않도록 한다.
- 문구는 안내문보다 실제 손님이 바로 이해할 수 있는 표현을 우선한다.

## 관리자 화면 규칙

- 관리자 화면은 운영 편의성이 우선이다.
- 메뉴 관리, 요청 확인, 이벤트 관리 흐름을 깨지 않는다.
- 목록 밀도, 버튼 크기, 스크롤 방식은 실제 운영 화면처럼 효율적으로 유지한다.
- 확인/처리/삭제 같은 상태 액션은 현재 정의된 운영 방식에 맞춘다.

## 요청 UI 규칙

손님 요청은 현재 두 종류로 나뉜다.

- `바로 전달하기`
- `특별한`

규칙:
- 두 요청 타입을 다시 하나로 합치지 않는다.
- 손님 화면에서는 두 요청 타입이 분리된 UX를 유지한다.
- 관리자 화면에서도 요청 보드를 분리된 단위로 유지한다.
- 요청 보드 슬라이드 UI는 현재 활성 위치를 직관적으로 표시해야 한다.
- 많은 요청이 쌓이는 경우 페이지 전체가 아니라 카드 내부에서 스크롤되도록 한다.

## 특별 요청 UI 규칙

특별 요청은 구조화된 폼 기반이다.

현재 필드:
- 성별
- 이름
- 나이
- 사는 곳
- 연락처(인스타그램)
- 이상형
- 하고 싶은 말

규칙:
- 관리자에서는 `남자`, `여자` 분리 구조를 유지한다.
- 특별 요청은 상태 처리보다 상세 확인과 삭제 중심 흐름을 우선한다.
- 특별 요청 관련 UI는 일반 요청 UI와 동일하게 단순 복제하지 않는다.
- 상세보기는 모달 흐름을 유지한다.

## 메뉴 관리 규칙

- 메뉴는 카테고리 기준으로 관리한다.
- 사용자가 원하지 않은 전체 필터, 과도한 옵션, 불필요한 제어는 추가하지 않는다.
- 메뉴 이미지, 대표 이미지, 크롭 흐름이 있는 경우 기존 방식을 우선 따른다.

## UI 작업 규칙

- 모바일 화면에서는 세로 길이와 밀도를 특히 주의한다.
- 카드, 버튼, 리스트는 사용자가 명시한 밀도와 크기를 우선 반영한다.
- 스크롤이 필요한 경우 페이지 전체 스크롤과 내부 스크롤을 구분해서 처리한다.
- 시각적으로 과하게 커지거나 운영 화면에서 비효율적인 배치는 피한다.
- 텍스트가 버튼이나 카드 영역을 넘치지 않도록 확인한다.

## 검증

- 사용자가 요청하지 않은 한 `npm run build`, `npm run lint`, 패키지 설치를 실행하지 않는다.
- 검증하지 않은 경우 최종 답변에서 명확히 밝힌다.
