# Database Skill

## 적용 범위

데이터베이스, 스키마, SQL, 마이그레이션 성격의 변경에 적용한다.

대상 예시:
- PostgreSQL 테이블
- `EnsureSchema`
- repository SQL
- 요청/특별 요청 저장 구조

## 기본 원칙

- 스키마 변경은 현재 실제 사용 중인 기능 구조를 반영하는 방향으로만 최소 적용한다.
- 기존 데이터를 깨뜨릴 수 있는 변경은 먼저 영향 범위를 설명한다.
- nullable 처리나 scan 에러가 발생하지 않도록 주의한다.
- 프론트/백엔드 타입과 DB 컬럼 구조를 함께 맞춘다.

## 현재 요청 데이터 구조

현재 요청 데이터 구조는 분리되어 있다.

- 일반 요청: `customer_requests`
- 특별 요청: `special_requests`

규칙:
- 특별 요청 관련 필드를 다시 일반 요청 테이블에 섞지 않는다.
- 일반 요청은 상태 관리가 필요하다.
- 특별 요청은 장부형 데이터로 보고 상세 확인과 삭제 중심으로 다룬다.
- 기존 분리 구조를 다시 합치지 않는다.

## 일반 요청 규칙

`customer_requests`는 `바로 전달하기` 요청을 저장한다.

주요 성격:
- 손님이 남긴 단문 요청
- 관리자 상태 흐름 존재
- `미처리`, `확인`, `처리완료` 상태 관리

## 특별 요청 규칙

`special_requests`는 `특별한` 요청을 저장한다.

현재 필드:
- `gender`
- `name`
- `age`
- `residence`
- `instagram`
- `ideal_type`
- `text`
- `created_at`

규칙:
- 특별 요청은 성별 기준으로 관리자 화면에서 분리된다.
- 상태 컬럼을 임의로 추가하지 않는다.
- 삭제는 특별 요청 전용 삭제 흐름을 사용한다.

## SQL 작업 규칙

- 기존 repository 메서드의 정렬 기준과 반환 타입을 존중한다.
- `NULL`이 가능한 값을 Go `string`으로 바로 scan하지 않는다.
- 필요 시 `COALESCE`를 사용하거나 DB 컬럼을 `NOT NULL`로 유지한다.
- 기존 데이터 이전 로직이 필요한 경우 재실행 가능성을 고려한다.

## 검증

- 사용자가 요청하지 않은 한 DB 명령, 빌드, 테스트를 실행하지 않는다.
- 검증하지 않은 경우 최종 답변에서 명확히 밝힌다.
